## Goals / Non-Goals

**Goals:**
- Carry the screenshot work only if it still adds functionality upstream lacks.
- If carried, one integration branch on current `main`, conflict-free with the approval change, with the catalog regenerated.

**Non-Goals:**
- Upstreaming the work.
- Keeping the two source branches alive as separate rebased branches.
- Deleting remote branches or backup tags (left to the user).

## Decisions

- **Gate before any rebase.** Compare upstream's `browser_screenshot_tab`, `definition.ts`, `mcp-tool-dispatch.ts` and CLI `tool.ts` at the then-current `main` with `f/screenshot-tab-integrated`. "Real functionality missing from upstream" means: upstream does not return the screenshot as an MCP image content part, or the CLI does not render image parts. A test-only difference (`f/restore-screenshot-tab-filepath`) does not count on its own. If nothing qualifies, the change ends: findings recorded in this folder, folder archived, nothing merged.
- **Recreate rather than rebase the integration branch.** Start `f/screenshot-tab-integrated` afresh from `main`, cherry-pick `f/screenshot-image-content-part-v2`'s single fork commit (`f9e48a93`; everything below it is upstream v0.0.111) and the extra `filePath` test if upstream lacks it, then the integration commit. Rebasing the old branch would drag the `b1e406d4` twin history.
- **Conflict with `approval-wait-visibility`.** Both change `mcp-tool-dispatch.ts`: the screenshot work makes `ToolCallResult.content` a `ToolContentPart[]` and calls `formatResult`; the approval change adds the per-call progress reporter and approval heartbeats in the same file. The branch is built on `main` and the conflict is resolved once, when merging into `exec-branch` after the approval and open-tab merges, keeping both behaviours; the dispatch tests of both changes must pass on `exec-branch`.
- **Generated catalog.** `browser-tools-catalog.ts` is regenerated by its generator, never hand-merged, on the branch and again on `exec-branch` if the merge touches it.
- **Branching and delivery.** This change folder is the first commit of the recreated `f/screenshot-tab-integrated` (copied from the holding folder outside the repository) and is ticked and archived there. If the gate drops the work, the folder is instead committed and archived on a short `f/rebase-screenshot-tab-branches` branch off `main` that is merged into `exec-branch`, so the decision is recorded with the other changes. Force-pushing `f/screenshot-tab-integrated` replaces the old remote branch and needs explicit user confirmation, with `--force-with-lease` against its backup tag.
- **No version bump.** Platform versions are owned by upstream's release process; the fork never tags or publishes.

## Risks / Trade-offs

- [Upstream adds an equivalent before this change runs] -> the gate drops the work.
- [Image content part changes what MCP clients receive by default] -> this is the intended behaviour of the branch; `filePath` remains for callers needing a file.
- [Conflict resolution breaks the approval heartbeat or progress ordering] -> the approval change's dispatch tests and e2e tests run on `exec-branch` after the merge.
